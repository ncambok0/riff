# RIFF 自動調査・非公開フィードバック連携：実装境界と設計案

対象：`ncambok0/riff` のドラフト PR #1。現行 `index.html` のみでは教育機関の自動調査と非公開クラウド同期を安全・確実に完了できないため、本書はサーバー機能の受け入れ条件を定義する。現行機能が実装済みであると誤認させない。

## 1. 現行実装と未実装

- 学校候補：追加・非表示・復元はブラウザの `localStorage` に記録。新規候補は「未調査（本人入力のみ・公式確認前）」と表示。公式サイトの内容の取得、検証、候補への自動入力は **未実装**。
- 感想：ブラウザの `localStorage` に記録し、CSV/JSONを書き出せる。新たに、利用者が指定した **Private GitHubリポジトリ** のIssue作成画面へ、保存済み回答を下書きとして渡す機能を追加。これは**自動投稿・自動同期ではない**。GitHub画面でプライバシーと内容を確認してから投稿する。リポジトリがPrivateかどうかはRIFF側では検証できず、利用者の確認に依存する。公開 `ncambok0/riff` を宛先とした自動転記は禁止。
- 実測・教材：ストップウォッチ、体感難易度、教材名・問題数・正答数をローカルに保存。3回以上の実測から所要時間中央値、同じ教材で3回以上の採点記録から観測正答率・体感難易度を表示する。これは本人の実測であり、教材難易度の外部客観評価・標準化ではない。

## 2. 教育機関を追加した後の調査ジョブ（次期）

必要な構成：認証付きフロントエンド → 認証付きサーバー/API → 公式サイトを探索・取得する調査ワーカー → 出典つきレビュー画面 → 承認後に候補へ適用するデータベース。ブラウザに調査サービスのAPIキー、GitHubトークン等を持たせない。

1. 「候補に追加」で学校名・公式URL候補・進学段階を保存し、`research_status=pending` とする。名前の似た別校・別キャンパスと混同しないよう公式のドメインと住所を照合。
2. サーバーで学校／募集要項の一次情報を収集し、対象年度・課程・校舎・コースを特定する。検索結果やAI生成文だけを根拠に確定しない。接続不能・robots・有料・認証が必要なページは未確認のまま停止する。
3. 既存カードと同じ項目（所在地、学べること、選抜条件、授業内容、費用、教員等）を **項目単位** で保存し、`value`, `source_url`, `page_title`, `checked_at`, `admission_year`, `confidence/status` を付ける。公式に未掲載の項目は空欄・未確認。著名卒業生・評価的な利点は無理に生成しない。
4. 自動作成したデータは `review_required` とし、利用者が出典を見て承認したフィールドのみ、候補カードへ反映する。学校公式の年度更新時には以前の確認済み情報を無断上書きしない。
5. 同名校・URL変更・学校統合・情報撤回への再調査、差分確認、修正履歴、削除／復元を用意する。

**合格条件**：誤った学校・年度の混同ゼロ、出典のない確定フィールドゼロ、未確認と検証済みを区別、追加・再調査・差分承認・キャンセル・アクセス不能のUIをテスト。

## 3. 感想のクラウド保存（次期）

- 推奨フロー：認証済みPrivateデータストア（例：適切なアクセス制御を設けたSupabase）へ本人が保存。開発用GitHubには本人が共有を選んだ、個人を特定しない改善内容だけをIssueとして連携。私的な学習記録や詳細な感想を公開リポジトリへ自動送信しない。
- API設計例：`POST /api/feedback`（本人トークンが必要、本文の入力検証・本人との関連付け）、`GET /api/feedback`（本人と許可された開発担当のみ）、`POST /api/feedback/:id/share`（明示的承認と公開可能項目の確認を必須とする）。
- データ：`feedback_id`, `app_version`, `respondent_role`（必要なら）、`created_at`, `answers`, `visibility`, `shared_at`, `issue_ref`。保存期間、削除、エクスポート、撤回を決める。ユーザーが「このチャットで見て」と依頼した際はアクセスを許可したコネクタで読み、ローカルデータを読めると装わない。
- 未成年者が利用することを前提に、非公開が初期値。GitHub連携時の公開先と投稿本文を事前プレビュー。ブラウザにGitHub PATを保存しない。
- GitHub Private Issueの既存の下書き導線は暫定策。自動同期と誤表示しない。長い本文はURLへ載せない。

## 4. 目標の期限と学習課題の扱い

- 一般的な「全件完了率」だけでなく、目標管理日までの対象課題をS/A/B・科目・出願条件・前提関係・復習必要性で分類する。
- 実測中央値は同じ作業が3回以上反復された場合の参考値。完了一回限りの作業や、途中まで実施済みの作業の**残り所要時間**は本人が調整する。教材・課題の複雑さにより初期見積もりが大きく変動し得る。
- 週予算×残週と対象未完了時間を比較し不足を提示するが、入試合否の判定や「不要」との自動断定はしない。本人／保護者が「計画に残す」「必要性を見直す」「今回は延期」を明示的に選ぶ。Sランクだけで必須判定しない。
- 未完了の「見直し待ち」は黙って削除せず、必要性の検証が終わるまで別集計で見せる。確定済みの今日のタスクは自動上書きしない。

## 5. 公開・運用のゲート

- GitHub PRのドラフトを維持し、実ブラウザ・スマートフォン、旧 `localStorage` の互換性、日付変更、リロード時の計測中データ、権限不足・Private確認漏れを確認してから `main` にマージする。
- Google Calendarや外部調査・データ同期は、ユーザーのアカウント接続とサーバー側の認証・情報取扱いの設計が完了するまで本番動作を有効にしない。
