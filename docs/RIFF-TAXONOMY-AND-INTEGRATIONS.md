# RIFF 共通分類・自動割当・外部連携設計（Draft v1）

> 対象: PR #1 作業版。実装状態の確定情報は `index.html` とその時点のコミットを優先。本書は仕様と今後の実装条件を整理する。公開中の `main` には未適用。

## 1. 共通の語彙と親子関係

| 名称 | 意味 | 共通性 |
| --- | --- | --- |
| タブ | 今日・計画・月別・ステージ・音楽・開発・学習・時間割・進路・感想などの画面 | UI |
| ジャンル | 音楽 / 開発 / 学習 | 全ジャンル |
| 学年 | 中1・中2・中3・高1・高2・高3。大学以降は未定 | 学習だけ |
| 科目 | 数学・英語・理科・社会・国語 | 学習だけ |
| ランク | S / A / B。苦手度と優先度は将来的には別フィールドで管理すること | 学習だけ |
| ステージ | ジャンル内の大項目 | 全ジャンル |
| ステップ | ステージ内の中項目 | 全ジャンル |
| やること | ステップ内の最小チェック可能項目 | 全ジャンル |

- 音楽・開発: ジャンル → ステージ → ステップ → やること。
- 学習: ジャンル → 学年 → 科目 → ランク → ステージ（単元群） → ステップ（学習項目） → やること。ランクは **ステップの属性** であり、ランクごとに別ステージを複製しない。
- 学習の「数と計算」はステージの **名称**。正負の数はステップの **名称**。従来の `unit` と `item` は表示用の元データとして保持する。
- `p1`〜`p8` は現在の2026〜2031年の**長期計画の時間区分**を表す既存キー。学習科目内の「ステージ1」と同じ番号空間ではない。新しいモデルでは `planPhaseId` と `stageId` を分ける。既存IDや保存済みチェック値を変更する移行は禁止。
- IDは表示名とは独立させる。改題・並べ替え・表示色変更でも、保存済みチェックと日次割当の参照を維持する。

## 2. 表示・色・タイポグラフィ

- ジャンル色: 音楽=紫、開発=緑、学習=青。ステップタグ・作業のフォーカス色に用いる。
- ステージ色: 既存ガントの `stageInfo[phase].color` と対応する色を使う。学習の科目内ステージでは、番号と元の計画フェーズを別々に記録し、どの配色規則によるものかを明示する。
- 1つの場所にステージ見出しを置く。個別ステップは「ステップN」だけを表示し、「ステージNステップN」を繰り返さない。
- 時間表記は「目安5分（仮）」「合計目安55分（仮）」とし、元の出所が不明な学習時間は「旧目安・算定根拠未確認」と区別する。
- 同じステージ・ステップ・やることIDは、今日・月別・ステージ・ジャンルのいずれから見ても同じ進捗を表す。親ステップの完了判定は「配下の必須やることがすべて完了したか」を派生計算し、元の学習単元チェックの既存値を勝手に変更しない。

## 3. タスクと見積もりのデータ

> 2026-10-01追記：教材・機材の正式な次期設計は [RIFF-ARCHIVE-DESIGN.md](./RIFF-ARCHIVE-DESIGN.md)、実測・反復・自動再計画は [RIFF-ADAPTIVE-PLANNING.md](./RIFF-ADAPTIVE-PLANNING.md) を優先する。以下は現行実装との互換説明を含む。

推奨フィールド: `id`, `genre`, `stageId`, `stepId`, `title`, `estimateMinutes`, `estimateSource`, `estimateUpdatedAt`, `actualMinutes`, `completedAt`, `rank`（学習のみ）, `grade`（学習のみ）, `subjectId`（学習のみ）, `materials[]`。

- `estimateSource`: `initial_heuristic`（現行のキーワード別初期値）, `user_adjusted`, `mentor_reviewed`, `measured` 等。
- 現行の音楽・開発の初期時間はキーワードに基づくヒューリスティック。例: 確認・設定・記録は概ね10分、制作・録音は概ね30分、開発の実装は概ね40分。指定済みの例外（HI-Z確認5分、入力バッファリング10分）を優先する。難易度調査・本人実測による校正は未実施。
- `actualMinutes` が未計測なら、見積もりを実績として表示しない。
- 将来の教材・資料は `materials[] = [{title, type, url, source, checkedAt, rights, notes}]` のように出典と確認日を保持。教材のページ番号・版・リンク切れを検証し、権利確認なしに全文や音源を再配布しない。

## 4. 今日の自動提案

1. 時間割を開始時刻順に読み、各枠のジャンルと所要時間を取得。英語など科目名が明記された場合は該当科目を絞る。
2. 必須の未完了タスクを、ジャンル別のステージ・ステップ・やること番号順に取り出す。期限や本人の優先指定は将来の拡張項目。
3. 見積もりの合計が枠を超えない範囲で提案。同じタスクを別枠に重複割当しない。短いタスクを優先して前提作業を飛ばすことはしない。
4. 確定した日次割当は日付とテンプレート指紋で保存。チェック時は自動で別タスクに置換せず、「未完了から再割当」でのみ再計算する。
   - 次期仕様では、安全な未来の未開始枠は実測・復習結果から原則自動再計画し、完了済み・実行中・過去・固定済み・手動固定の予定は保護する。詳細は適応型計画仕様を参照。
5. 変更はステップ選択 → やること選択の順。計画外タスクは当日限りで保持し、既存の計画IDを偽造しない。
6. クリックは同一タスクIDを使って該当ジャンルの詳細へ移動し、そのタスクだけをハイライトする。タスクのチェック値は全画面で共通。
7. 将来: 予定の余白（例5〜10分）、前提タスク、締切、実績時間に基づく補正、本人が拒否した作業の再提案抑制を検討する。本人の承認なしに長期計画の優先度や期限を変更しない。

## 5. 外部連携とプライバシー

### Google カレンダー

- 技術的には可能。初期段階は時間割からの一方向の予定エクスポート（ICS）と、Google カレンダーへの取り込みを分ける。
- 自動登録・変更・双方向同期にはGoogleアカウントのOAuth同意、限定した権限、認証情報を扱うサーバー処理、重複防止用のイベントID、タイムゾーン、日本の祝日と夏時間の扱い、失効・削除時の仕様が必要。
- 未来のテンプレート予定と、実際に確定した当日の予定を混同しない。無断でカレンダーへ大量登録しない。

### 進路の教育機関

- 既存候補の非表示／復元と新規候補のローカル登録は実装されている。追加候補に公式未確認の情報を自動で補って「確認済み」としない。
- 同等情報の収集には、確認した公式URL、アクセス日時、募集年度、原文に基づく根拠、要確認点を保存する調査ワークフローが必要。学校・コースの情報が食い違うときは未確定で保持する。
- バックエンドと情報取得方法を決めてから、自動収集／レビュー後に公開する二段階の仕組みを作る。

### 感想とGitHub

- 現行の感想は `localStorage` に保存。CSV/JSON・テキストのエクスポートがあるが、**GitHubへ自動保存されない**。
- `ncambok0/riff` は公開リポジトリ。未成年利用者の感想・学習履歴・個人情報を公開Issueやリポジトリファイルへ自動アップロードしない。
- 安全な候補: 私有データを認証付きバックエンド（Supabase等の適切なアクセス制御）に保存し、公開して問題のない内容だけを利用者が明示的に選んでGitHub Issueへ送信する。あるいは専用の非公開GitHubリポジトリで権限を限定する。
- ブラウザのHTMLやlocalStorageにGitHub Personal Access Tokenを埋め込まない。OAuthトークンなどの秘密情報はサーバー側で管理。
- このチャットで参照するFBは、権限のあるGitHub Issue/PRまたは接続済みの安全なデータソースから読む。チャットが自動でブラウザのlocalStorageを読めると誤認させない。

## 6. 受け入れ検査

- 10タブ × 過去・現在・未来の日付で表示処理、カードの順番、月ラベル27+28、ジャンプ先、ハイライト、複数回ジャンプ時の古い展開解除を確認。
- 日次自動割当: 時間枠超過なし、重複なし、順序維持、完了後の固定、科目指定、手動差し替え、計画外入力、空枠、時刻不正を検査。
- localStorage既存データ互換と、日付変更・テンプレート編集・端末再読込・モバイル画面を実ブラウザで確認。
- Google カレンダー／外部調査／GitHubへのアップロードは、認証・プライバシー設計の合意があるまで未実装と明記する。
